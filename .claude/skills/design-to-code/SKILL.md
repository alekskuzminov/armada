# Design to Code

## Purpose

Используй этот skill, когда нужно:
- перенести блок из Figma в код
- реализовать секцию по макету
- сверстать новый UI-блок по референсу
- привести существующую реализацию ближе к дизайну
- подготовить production-ready разметку под корпоративный сайт

## When to use

Используй skill в случаях:
- "перенеси этот экран в Next.js"
- "сверстай hero по макету"
- "реализуй секцию из Figma"
- "повтори структуру блока по референсу"
- "сделай адаптивную версию этого дизайна"

Используй этот skill, когда главное:
- есть визуальный источник истины
- нужно перевести композицию, иерархию и адаптив из дизайна в код
- важно сохранить логику макета, а не просто дать каркас компонента

Не используй этот skill для:
- написания всех текстов страницы с нуля
- настройки CRM и webhook-интеграций
- полного SEO-аудита
- предрелизного review всего сайта
- общей структуры страницы по брифу без макета
- простого scaffold компонента без дизайн-источника
- service page как контентного deliverable без визуального источника

Если макета нет и нужен только каркас компонента, предпочитай `component-scaffold`.
Если нужна структура страницы по смыслу, предпочитай `page-from-brief`.
Если нужна именно service page с контентом и SEO-логикой, предпочитай `service-page-generator`.

## Inputs to analyze

Перед генерацией кода проанализируй:
- визуальную иерархию блока
- назначение секции
- primary CTA и secondary CTA
- плотность контента
- сетку и контейнер
- desktop / tablet / mobile поведение
- повторяющиеся UI-паттерны
- есть ли в проекте уже похожий компонент

## Instructions

1. Сначала опиши структуру блока:
   - контейнер
   - левая/правая колонка
   - media area
   - text content
   - CTA area
   - trust/proof area
   - background/decorative layer, если есть

2. Перед реализацией проверь:
   - есть ли в проекте существующий section wrapper
   - есть ли готовые кнопки, headings, cards, badges, form controls
   - можно ли переиспользовать существующие токены и utility-классы

3. При переносе дизайна в код:
   - не гонись за буквальным pixel-perfect, если это ломает адаптив или усложняет код
   - сохраняй визуальную логику и иерархию
   - делай код читаемым и модульным
   - не создавай лишние вложенности div без пользы
   - используй семантические теги там, где это уместно

4. По умолчанию:
   - предпочитай Server Component
   - Client Component используй только если нужен интерактив
   - не выноси слишком рано микрокомпоненты, если блок используется один раз

5. Для адаптива:
   - сначала думай о содержании, потом о breakpoint-логике
   - не допускай ломания ритма отступов
   - не оставляй критичный текст в слишком узкой колонке
   - CTA должен оставаться заметным на мобильном

6. Если макет неполный:
   - укажи, какие решения ты принял самостоятельно
   - пометь спорные моменты как предположения
   - предложи безопасный B2B-вариант реализации

7. После генерации кода обязательно дай:
   - краткое описание структуры
   - что проверить визуально
   - где возможны расхождения с макетом
   - какие части можно потом переиспользовать

8. Если в рамках задачи были внесены изменения в код, не считай работу завершённой без проверки:
   - типов
   - линта
   - сборки
   Если какая-то проверка не запускалась, явно скажи об этом.

## Output format

1. Что реализуется
2. Какие файлы будут созданы или изменены
3. Предлагаемая структура блока
4. Код
5. Что проверить после вставки
6. Что можно улучшить во второй итерации
7. Какие проверки выполнены

## Quality bar

Результат должен:
- быть реалистичным для production
- соответствовать спокойному корпоративному стилю
- быть адаптивным
- не конфликтовать с существующей дизайн-системой
