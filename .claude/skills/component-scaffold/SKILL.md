# Component Scaffold

## Purpose

Используй этот skill, когда нужно:
- создать новый React/Next.js компонент
- подготовить каркас локальной секции
- выделить переиспользуемую компонентную структуру
- привести разрозненный UI к единому паттерну
- быстро подготовить scaffold перед наполнением контентом

## When to use

Используй skill в случаях:
- "собери reusable component"
- "подготовь scaffold компонента"
- "сделай каркас секции"
- "собери карточку услуги"
- "сделай layout для локального блока"
- "вынеси это в отдельный компонент"

Используй этот skill, когда главное:
- определить безопасную структуру компонента
- выбрать server/client boundary
- переиспользовать существующие UI-паттерны проекта
- быстро получить рабочий каркас под дальнейшее наполнение

Не используй этот skill для:
- pixel-perfect переноса Figma или референса в код
- hero-секции, если у пользователя есть макет или скрин
- генерации полной структуры страницы
- генерации service page с текстами и SEO-структурой
- глубокого SEO-аудита
- копирайтинга всей страницы
- финального релизного ревью
- форм с интеграцией данных

Если у пользователя есть явный макет, референс или запрос "перенеси из Figma", предпочитай `design-to-code`.
Если нужен план страницы по брифу, предпочитай `page-from-brief`.
Если нужна именно service page с контентной логикой, предпочитай `service-page-generator`.
Если основная задача в форме и submit flow, предпочитай `form-integration`.

## Instructions

1. Сначала определи назначение компонента:
   - информационный
   - конверсионный
   - навигационный
   - доверительный
   - контентный

2. Проверь существующие паттерны проекта:
   - есть ли похожий компонент
   - есть ли канонический стиль секций
   - есть ли готовые UI-примитивы, которые нужно переиспользовать

3. Перед генерацией кода кратко опиши:
   - что будет создано
   - какие файлы будут затронуты
   - будет ли компонент server или client component

4. При создании компонента:
   - предпочитай простую и читаемую структуру
   - соблюдай TypeScript typing
   - не добавляй лишние абстракции
   - не делай client component без реальной необходимости
   - соблюдай семантическую HTML-структуру
   - учитывай accessibility
   - учитывай адаптив desktop / tablet / mobile

5. Для локальных секций включай:
   - heading
   - supporting text
   - основной CTA при необходимости
   - secondary CTA при необходимости
   - proof / trust content если это уместно

6. Если контент не предоставлен:
   - используй нейтральные временные плейсхолдеры
   - явно помечай, что это временный контент

7. После генерации обязательно дай:
   - краткое объяснение решения
   - список того, что проверить визуально
   - что стоит вынести в props
   - что может быть переиспользовано дальше

8. Если в рамках задачи были внесены изменения в код, не считай работу завершённой без проверки:
   - типов
   - линта
   - сборки
   Если какая-то проверка не запускалась, явно скажи об этом.

## Output format

Отвечай в таком порядке:
1. Цель компонента
2. Какие файлы создаются или меняются
3. Код
4. Что проверить после вставки
5. Возможные улучшения
6. Какие проверки выполнены

## Quality bar

Результат должен:
- выглядеть как production-ready код
- быть понятным без лишних комментариев
- быть пригодным для повторного использования
- не ломать существующий стиль проекта
